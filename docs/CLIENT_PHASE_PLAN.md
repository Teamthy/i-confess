# Client build — phase plan

Building Flutter and Next.js clients, phase by phase, against a verified API
contract.

## Verification reality

I set this out plainly because it changes what each phase can promise.

| Layer | Can I verify it here? |
|---|---|
| OpenAPI spec | **Yes** — generated from the live route table, contract-tested in Go |
| Dart API client | **Yes** — Dart SDK installed to `/tmp`, analyzed and unit-tested |
| Dart domain/state logic | **Yes** — pure Dart, testable without Flutter |
| Flutter widgets | **No** — needs the Flutter SDK (~1.5 GB) and a simulator |
| Next.js logic | **Partially** — TypeScript type-checking, if dependencies stay minimal |
| Next.js rendering | **No** — needs `node_modules` and a browser |

The strategy follows from that: **push as much logic as possible below the UI
layer**, where it can be tested, and keep widgets thin. That is good
architecture anyway (§57 asks for exactly this), and here it also means most of
the codebase is verified rather than merely written.

Toolchains live in `/tmp`, never the workspace. The Dart SDK is 203 MB; the
workspace stays at ~3 MB of source.

## Phase 0 — API contract ✅ complete

**`contracts/openapi.json`** — 70 paths, 97 operations, generated by
`go run ./cmd/genspec`.

The spec is emitted from the router's own registration calls. `h.route(...)`
wires the handler *and* records it, so an endpoint cannot be served without
being described. Six Go contract tests enforce this:

- every served route appears in the spec
- authenticated routes declare `bearerAuth`; public routes must not
- operation ids are unique — a collision would silently overwrite a generated
  method
- every route has a summary
- path placeholders are declared
- 401/402/429 are documented, so a generated client can distinguish "upgrade to
  Premium" from "something went wrong"

**`clients/dart/`** — typed client, **14/14 tests passing** against a real
local HTTP server rather than a mock. Mocks would prove the client calls a fake
the way the test expects; they prove nothing about sockets, status codes and
headers, which is where the bugs are.

Three decisions worth recording:

**Concurrent refresh is collapsed onto one attempt.** This is the subtle one.
The server rotates sessions and detects reuse — so if a phone waking from sleep
fires five requests that all 401, five parallel refreshes would make four of
them replay an already-rotated token. The server would correctly read that as
theft and revoke the whole family, signing the user out for doing nothing
wrong. A single in-flight future prevents it, and a test asserts exactly one
refresh occurs across three concurrent 401s.

**Offline is not an auth failure.** `NetworkException` is a separate type from
`ApiError`. Showing "invalid password" when someone is on a train is a common
client bug, and it makes people change a password that was never wrong.

**Token storage is an interface with no default.** A token is a bearer
credential: on device it belongs in the Keychain or Keystore, never
SharedPreferences, which is readable on a rooted phone and survives in
plaintext backups. `InMemoryTokenStore` exists for tests and is documented as
unfit to ship.

Zero runtime dependencies — `dart:io` and `dart:convert` only. A credential
client should not drag a transitive package tree into an app.

## Phase 1 — Flutter domain and data layers (next)

Everything below the widget tree, which is the part I can actually test:

- `SecureTokenStore` backed by Keychain/Keystore
- Repositories: auth, profile, sessions, library, downloads
- Domain models mapped from API responses
- State machines for the states §58 requires: `initial · loading · loaded ·
  updating · error · offline`
- Offline cache with an explicit staleness policy (§102): show cached data,
  never claim a write succeeded before the server confirms

Verified with `dart test`. No Flutter import in any of it.

## Phase 2 — Flutter presentation

Widgets, navigation, the player. **Unverifiable here** — I will say so in the
handover rather than implying otherwise, and keep widgets thin so the untested
surface is as small as possible.

## Phase 3 — Next.js foundation

Typed TS client generated from the same spec, cookie-session handling, route
protection, and the CSRF layer that becomes necessary the moment cookies are
used (deliberately not pre-built in the backend, because CSRF written against
an imagined cookie scheme is usually wrong).

## Phase 4 — Next.js web + admin surfaces

Profile, preferences, library, subscription, security, devices; then the admin
console.

## Running Phase 0 yourself

```bash
# Regenerate the spec from the live routes
cd server && go run ./cmd/genspec ../contracts/openapi.json

# Verify the Dart client
cd clients/dart && dart pub get && dart analyze && dart test
```
